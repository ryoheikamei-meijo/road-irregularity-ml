# 11.10 の企業 MTG（押しスト）に向けた整理：今年の範囲とシステムの構成

11 月 10 日（火）の企業 MTG で、システム（アプリ・サーバー・地図）の方針を相談する。その前に、今年の研究の範囲と、決めること・聞くことを整理した。

- 今年の研究の範囲は、先生とも合わせる（第 17 回ゼミの指摘「今年の研究でどこまでやるかを決める」への答え）。
- サーバーの環境（Cloudflare か AWS か）は、企業側の環境と費用の持ち方を聞いてから決める。

## サマリ

- **今年の範囲**：ML（特徴量・モデル）は、今の core・SVM・2.0 秒でいったん固定する。残りの期間で、**アプリで判定 → サーバーに送る → 地図に出す**システムを作り、**実際に使って評価する**。映像の切り出し、体重・車椅子の違いへの対応は、今後の課題（後輩への引き継ぎ）に回す。
- **決めたこと**：判定はスマホで行う。判定結果はすぐ、生データは走行後に送る。卒論までは自分と研究室だけが使う。Web の地図は関係者だけが見られるようにする。
- **今の案**：試作は Cloudflare（Workers + D1 + R2 + Pages）。期限のない無料枠で足り、引き継ぎで無料期間が切れる心配がない。AWS に移すことになっても困らない作りにする。
- **来年以降の運用**：入れ物は Terraform、コードと DB の表の形は wrangler、データはバックアップで守る。Terraform への移行は、構成が固まってから（4 章）。
- **MTG で聞くこと**：「押しストに入れる」の意味、アプリの分け方、地図はスマホと Web のどちらを優先するか、企業側の環境、費用と管理、データの扱い、地図の土台、評価のしかた（3 章）。

## 1. 今年の研究の範囲

| 7〜9 月 | ML の検討・実装・比較 | 10〜11 月まで続いた（特徴量の設計、ジャイロ、ラベルの見直し、体重の確認） |
| 10 月 | 映像の切り出し | 手を付けていない |
| 11 月 | システム全体の評価 | – |

| 1 月 | 卒論の要旨、情報処理学会の全国大会の原稿 | – |
| 2 月 | 卒論の提出、発表会 | – |

今のアプリ（`MyApplication3`）は、センサーを記録して CSV に保存するだけ。判定・送信・地図の機能は無い。逆算すると、開発と評価に使えるのは、あと 6〜7 週間くらい。

### ML を固定して、システムを作る理由

1. **ML の改善は、伸びしろが小さくなっている**。直近の改善は rough 0.91 → 0.92 程度（[rough の原因](../2026-11-05/20261105_rough_error_analysis.md)）。残る問題は、ラベルの定義（STOP 側のずれ）とデータの幅（体重・車椅子）で、アルゴリズムより測り直しが要る。
2. **先生も企業側も、システムを求めている**。
   - 先生（第 17 回ゼミ）：残りの期間で Android アプリを作り、実際に使うところまでやる。車椅子・体重の差は、後輩に引き継いでもよい。
   - 企業 MTG（10.6）：ゴールは押しストに入れること。大月さん「地図を作るには、ある程度よい精度に来ている」。
3. **車椅子が変わる予定**。押しストで使うのは自走式で、今の介助用の車椅子とは違う（10.6 の企業 MTG）。今の車椅子に合わせて細かく詰めても、そのまま使えない可能性が高い。
4. **研究テーマが「路面凹凸検出結果の可視化」**。地図に出すところまでないと、テーマの後半が抜ける。
5. **今の評価に足りない部分を、システムが埋める**。今の評価（方針A）は、ラベルの区間の中の窓だけを使い、段差の手前や凸凹と flat の境目の窓を捨てている。連続で走ったときの誤検知や、位置のずれは、システムを動かさないと測れない。

### 日程（案）

| 期間 | やること |
| --- | --- |
| 11/9〜11/22 | **アプリで判定する**。core の 5 つの特徴量と SVM をアプリに移し、走りながら flat / step / rough を出す。PC での判定と同じ結果になるかを確かめる |
| 11/23〜12/6 | **送信・保存・地図**。判定結果と GPS を送って保存し、地図に表示する（最小限の作り） |
| 12/7〜12/20 | **実際に使って評価する**。段差・凸凹の位置が分かっているコースを連続で走り、検出率、flat での誤検知、位置のずれを測る。ウィリー・坂道の測定（[段差の傾き](20261108_step_tilt.md) の 5 章）も一緒に行う |
| 12/21〜 | 卒論の執筆。1 月に要旨と全国大会の原稿 |

- 間に合わない場合の優先順位：**アプリで判定 → 実際に使って評価 → 地図 → 自動送信**。地図は「走り終わってから PC でまとめて表示する」に落としても、評価は残せる。
- 後に回すもの：映像の切り出し、体重・車椅子の違いへの対応（[重りの測定の計画](../2026-11-02/20261102_load_measurement_plan.md)、[周波数帯の特徴量](20261108_band_core_eval.md)）、ML の細かい改善（実際に使って見つかった問題に絞る）。

## 2. システムの方針（壁打ちで決めたこと）

| 項目 | 決めたこと | 理由 |
| --- | --- | --- |
| 地図を見る人 | 車椅子の利用者・介助者・企業の人・研究者の全員 | – |
| 判定する場所 | **スマホ** | 今の SVM は特徴量 5 つで、アプリに移しやすい。サーバーは「受け取って保存し、返す」だけでよい |
| 送るもの | 判定結果と GPS、**生データも** | 生データは、再学習や後輩の研究に使う |
| 送る時期 | **判定結果はすぐ、生データは走行後にまとめて** | 生データは大きい（下の見積もり）。Wi-Fi のときに送れるようにする |
| 使う人 | **卒論までは自分と研究室だけ** | 本格的なログインや同意の仕組みは後回し。ただし、誰でも書き込める状態は避ける（アプリに送信用のキーを持たせる程度） |
| Web の地図 | **関係者だけが見られるようにする** | 位置と日時から、誰がいつどこにいたかが分かるため |
| 地図をスマホと Web のどちらで先に作るか | **MTG で聞く** | 利用者向けならスマホ、企業での確認・分析なら Web |

### データ量の見積もり

- 生データ（acc・gyro・linear_acc など）は、1 秒あたり約 90 KB（1 分で約 5.5 MB）。11.1 のセッションで実測（例：140 秒で 12.7 MB）。
- これまでの記録は 1〜2 分だったが、実際に使うと 1 回 10〜30 分で、**1 回 50〜160 MB**。合計 10 時間走ると約 3.3 GB。
- 判定結果は、2.0 秒の窓を 0.5 秒ずつずらすと 1 秒に 2 件。1 時間で 7,200 件、1 件 100 バイトとして約 0.7 MB。
- 費用に効くのは、生データの保存の容量。圧縮して送れば小さくなる（CSV は圧縮が効きやすいが、どのくらい小さくなるかは未確認）。

### データの形（案）

| 表 | 中身 |
| --- | --- |
| 走行（session） | 日時、端末、車椅子の種類、体重、アプリとモデルのバージョン |
| 判定結果（detection） | 走行、時刻、緯度・経度、GPS の精度、クラス、確からしさ、窓の長さ |
| 生データ（raw） | 走行、ファイルの場所（オブジェクトストレージのキー）、大きさ、送った日時 |

- モデルのバージョンを記録しておくと、後でモデルを変えたときに、結果を比べられる。
- 同じ場所を何度も通ったときの表示（1 回ずつの点か、まとめて出すか）は、作りながら決める。

## 3. MTG で聞くこと

1. **「押しストに入れる」とは具体的に何か**。押しスト側に、すでにアプリや機器があるのか。判定の機能を、どこに組み込む想定か。
2. **アプリの分け方**：今の計測用のアプリ（ボタンでラベルを付ける、研究用）とは別に、利用者向けのアプリ（判定と地図）を作る形でよいか。
3. **地図はスマホと Web のどちらを優先するか**。
4. **サーバーの環境**：企業側に、すでに使っている環境（AWS など）や、載せたい先があるか。なければ、試作は Cloudflare の無料枠で作ってよいか。
5. **費用と管理**：本番の費用を誰が持つか。卒業後に誰が管理するか（研究室か企業か）。
6. **データの扱い**：位置と日時の入ったデータを、誰が見てよいか。将来ほかの利用者に使ってもらうときの、同意の取り方。
7. **地図の土台**：Google マップか OpenStreetMap か。押しスト側に決まりがあるか。
8. **評価のしかた**：10.6 の MTG の「梅津さんが合っていると言える程度」の精度を、どう確かめるか。例えば、決まったコースを走って、検出した段差・凸凹の位置が合っているかを見る。検出したい段差の例（梅津さんの写真、8.5 の MTG）とも合わせる。

## 4. サーバーの環境の比較

無料枠の条件は、ほとんどが解説記事（二次資料）からの情報。決める前に、公式の料金ページで確かめる。

| 候補 | 構成の例 | 無料枠 | 気をつける点 |
| --- | --- | --- | --- |
| **Cloudflare** | Workers（API、TypeScript・Hono など）+ D1（DB）+ R2（ファイル）+ Pages（Web の地図）+ Access（閲覧の制限） | Workers 1 日 10 万リクエスト、R2 10 GB・転送無料（二次資料）。D1 は、2026/9/1 から無料枠を超えるとクエリが失敗する（公式の更新履歴） | 期限なしで無料のまま使える。R2 は S3 と同じ API。R2 の 10 GB は、生データで約 30 時間分 |
| **AWS** | Lambda + API Gateway + DynamoDB + S3 | 2025/7/15 以降の新しいアカウントは、最大 $200 のクレジットと、最長 6 か月の無料プラン。Lambda・DynamoDB には期限のない無料枠（二次資料、AWS 公式のページで確認が要る） | 無料プランは 6 か月で終わり、有料プランに切り替えないとアカウントが閉じる。クレジットカードの登録と、持ち主が要る。企業が AWS を使っているなら合わせやすい |
| Supabase | Postgres（PostGIS）+ ファイル置き場 + ログイン | DB 500 MB、ファイル 1 GB（二次資料） | 7 日間使わないと止まり、手で再開が要る。ファイル 1 GB は生データ約 3 時間分 |
| Firebase | Firestore + Cloud Storage | Firestore は無料枠あり | ファイル置き場（Cloud Storage）は、従量課金のプラン（支払い方法の登録）が必須（公式の FAQ） |

### 今の案

- 企業側に希望の環境がなければ、試作は **Cloudflare** で作る。
  - 期限のない無料枠で、試作の規模（研究室だけ、数十時間の走行）なら足りる。
  - API・DB・ファイル・Web の地図・閲覧の制限を 1 か所にまとめられる。
  - 引き継ぎで「無料期間が切れてアカウントが閉じる」心配がない。
  - Cloudflare・AWS とも使った経験があり、TypeScript で API を書ける。
- **AWS に移すことになっても困らない作りにする**。
  - API は Hono で書く（AWS Lambda でも動く）。
  - 生データは、S3 と同じ API の R2 に置く。
  - DB の表の形（2 章）を決めておく。
- アカウントは、個人のものではなく、研究室で引き継げるもの（研究室のメールアドレスなど）で作る。

### 来年以降も運用できるようにする（Terraform）

Cloudflare の環境を Terraform で作っておけば、来年以降も同じ環境を作り直しやすい。ただし、次の 4 つは Terraform だけでは守れないので、別に用意する。

1. **データは戻らない**。Terraform が作り直すのは入れ物（D1 のデータベース、R2 のバケット、Workers、Pages、Access の設定など）だけで、中のデータ（判定結果、生データ）は戻らない。`terraform destroy` で消すと、中のデータも一緒に消える。環境を落とす前に、D1 は `wrangler d1 export` で SQL に書き出し、R2 は別の場所（研究室の NAS など）にコピーする。
2. **そもそも落とさなくてよい可能性が高い**。無料枠は、使っていなければ費用がかからない。費用のために落とす必要はほぼなく、落とすとデータを消す危険のほうが大きい。止めたいだけなら、Workers の公開を止める、Access で閉じる、で足りる。
3. **Terraform の状態ファイル（state）の置き場所**。自分の PC に置いたままだと、卒業後に誰も Terraform で管理できなくなる。R2（S3 と同じ API なので、Terraform の S3 バックエンドとして使える）や、HCP Terraform の無料枠など、研究室で引き継げる場所に置く。state には秘密の値が入ることがあるので、公開しない場所にする。
4. **Terraform の外にあるもの**。
   - Cloudflare のアカウント自体は Terraform で作れない。研究室で引き継げるアカウントで作る。
   - Terraform を動かすための API トークンは、作り直す手順を README に書いておく。
   - D1 の表の形（マイグレーション）は `wrangler d1 migrations`、Workers のコードのデプロイは wrangler で行うのが普通。

道具の分け方（案）：

| 管理するもの | 道具 |
| --- | --- |
| 入れ物（D1・R2・Pages・Access・DNS） | Terraform |
| Workers のコード、D1 の表の形 | wrangler（コードと一緒に Git で管理） |
| データ | 定期的なバックアップ（D1 の書き出し、R2 のコピー） |
| 手順 | README（後輩が 1 から作り直せるように） |

- Cloudflare の Terraform のプロバイダーは、大きなバージョンアップで書き方が変わることがある（v4 → v5 で大きく変わった）。来年も同じ書き方で動くように、バージョンを固定する。
- **進め方**：卒論までの期間で、Terraform の整備に時間をかけすぎない。最初は wrangler で作って動かし、構成が固まってから Terraform に移す（または、引き継ぎの作業として最後にまとめる）。

## 5. 先生と合わせること

- 今年の範囲：ML を固定し、システムを作って、実際に使って評価する（1 章）。
- 後に回すもの：映像の切り出し、体重・車椅子の違いへの対応。後輩に引き継ぐなら、何を残すか（メモ、データ、スクリプト）。
- 卒論の評価の軸：オフラインの精度（今の評価）と、実際に使ったときの検出率・誤検知・位置のずれ。
