# 窓ごとの判定を、地図に出すために「まとめる」：設計判断（相談用）

アプリの判定は、2.0 秒の窓を 0.5 秒ずつずらして出す。このまま地図に印を出すと、1 つの段差に何十個も印が並ぶ。続いた窓を 1 つの「イベント」にまとめて、印を減らしたい。この文書は、まとめ方を、これまでの計測（16 走行）で調べた結果と、そこから私が考えた案をまとめたものである。**案についての意見がほしい**（末尾の「相談したいこと」）。

**状態**：分析は済み。案は暫定で、アプリには入れていない。

## 何が問題か

- 窓は 0.5 秒ずつずれるので、1 つの衝撃が、最大 4 つの窓に入る。
- さらに、段差のラベルは「衝撃の 0.5 秒前から STOP を押すまで」で、モデルはその区間全体を「段差」と判定する。そのため、衝撃のあとの数秒間も、段差の窓が続く。
- 16 走行（合計 27.9 分）を、その走行を除いて学習したモデルで判定すると、**段差と判定した窓が 1,470 個、凸凹が 730 個**あった。正解の通過は、段差が 145 回、凸凹が 58 回である。まとめなければ、1 回の段差の通過に、印が約 10 個並ぶ。

## 一般的なまとめ方と、選んだもの

連続した窓を分類するときの後処理として、次のものが一般的だと考える（関連研究は調べていない。下の「限界」）。

| 方法 | 内容 | このリポジトリでの扱い |
| --- | --- | --- |
| 多数決・中央値フィルタ | 前後の窓で多数決を取る | 見送り。2026-05-19 の分析で、多数決だと短い段差が平坦や凸凹に埋もれるため、段差を優先する規則にした経緯がある（`docs/knowledge/2026-05-19/phase1_baseline_pipeline_summary.md`） |
| 続いた窓を 1 つのイベントにする | 同じクラスが続く窓を 1 つにまとめる。間に他のクラスが少し挟まっても、つなぐ。短いものは捨てる | **採用の候補**。パラメーターは「つなぐ幅 gap」と「最低の窓の数 min_n」の 2 つ |
| 代表を 1 つにする | イベントの中で、決定関数の値が最大の窓を代表にし、印を 1 つ立てる | **採用の候補**（上と組み合わせる） |
| 系列モデル（HMM など） | クラスが切り替わることにペナルティを付けて、最もありそうな並びを求める | 見送り。今の規模には重い |
| 場所でまとめる | 地図を格子や道路の区間に分け、通った回数に対する検出の割合を出す | 次の段階（サーバーから複数の走行を読み出すとき） |

まとめ方（クラスごとに、段差と凸凹を別々に行う）：
1. **gap**：そのクラスの窓の間に、ほかのクラスの窓が gap 個以下しか挟まらなければ、つなげて 1 つにする（gap = 0 は、続いた窓だけ）。
2. **min_n**：つないだあと、元の窓が min_n 個に満たないイベントは捨てる。
3. **代表**：イベントの中で、そのクラスの決定関数の値が最大の窓の中心を、印の位置にする。

## 調べ方

- **判定**：leave-one-session-out。その走行を除いた 15 走行で学習した SVM（core の 5 個の特徴量、傾きの基準は startmean10＝アプリの `v4_20261118` と同じ）で、その走行の**全部の窓**（ラベルの無い窓も）を判定した。学習済みのモデルで全走行を判定すると、学習に使った走行を判定することになり、結果が甘くなるため。ラベルのある窓での一致率は 0.953。
- **正解**：段差は、通過ごとの衝撃の時刻（通過の区間で |z| が最大の時刻）。凸凹は、ラベルの区間（START + 1 秒〜STOP）。取り消した通過と、除外した通過（`configs/sessions/excluded_passes.csv`）は数えない。
- **指標**
  - **再現率**：正解の通過のうち、対応するイベントがあるもの。段差は、イベントの範囲が衝撃の ±1 秒に重なれば、対応するとした。凸凹は、区間に重なれば対応するとした。
  - **1 通過あたりのイベント数**：1 に近いほど、印が重複していない。
  - **複数の通過をまとめたイベント**：1 つのイベントが 2 つ以上の通過に対応したもの（まとめすぎの目安）。
  - **誤検知**：どの通過にも対応しないイベント。1 分あたりの数で出す。flat の走行（合計 7.2 分）だけでも出す。
  - **位置のずれ**：段差の印と衝撃の時刻の差（秒）。走っている間の GPS の速度の中央値が 0.97 m/s なので、秒数はほぼメートルと読める（10/31 の走行には GPS が無く、11/1 の走行から求めた）。
- 再現：`uv run python -m src.experiments.e20261119_window_merge`（結果は `data/analysis/20261119_window_merge/`）。

### 分かったこと

1. **まとめると、印は大きく減る**。段差は 1,470 → 162、凸凹は 730 → 67（gap 0・min_n 3）。再現率は落ちない。
2. **gap を増やすと、位置が大きくずれる**。段差の通過は、同じ走行の隣り合う通過の間隔が、中央値で 4.2 秒、最短で 2.8 秒しかない（同じ段差を上り下りした計測のため）。gap を 1 にするだけで、隣り合う通過をつないでしまい、印が減る（162 → 105）代わりに、位置のずれが 0.9 秒から 2.6 秒に増える。
3. **min_n を上げると、誤検知が減る**。min_n 1 → 3 で、flat の走行での誤検知が 2.66 → 0.70（/分）になる。min_n 4 にすると 0.42 になるが、再現率が下がる。
4. **決定関数の値による足切りは、効かなかった**。イベントの最大値に下限（0〜1.5）を付けても、誤検知は変わらなかった。誤検知のイベントも、最大値は十分に大きい。
5. **印の位置を \|z\| が最大の時刻にすると、gap 0 では、位置のずれの中央値が 0 になる**。ただし、正解の衝撃の時刻自体が、\|z\| が最大の時刻として決めたものなので、これは同じ定義で測っているだけで、実際の精度を表さない（上位 10% のずれが 4.1 秒あるのは、複数の通過をまとめたイベントのため）。

## 暫定の案と、その理由

**案**：段差も凸凹も、**gap 0（続いた窓だけをまとめる）、min_n 3（3 つ以上続いたものだけを採る）**。印の位置は、決定関数の値が最大の窓の中心にする。

| 判断 | 理由 |
| --- | --- |
| gap は 0 | 段差の通過は、3〜4 秒おきに続くことがある。つなぐ幅を増やすと、別々の段差を 1 つの印にまとめてしまい、位置も大きくずれる（上の分かったこと 2）。重複した印（1 通過あたり 1.19 個）は残るが、見た目の問題で、位置の誤りよりも軽いと考えた |
| min_n は 3 | 1 や 2 だと、flat の走行で誤検知が多い（2.66・2.10 /分）。4 だと、再現率が下がる（凸凹 0.966）。3 は、再現率を保ったまま、誤検知を 0.70 /分に下げられる |
| 段差は点、凸凹は区間 | 段差は短い瞬間のイベントなので、印を 1 つ。凸凹は続く路面の状態なので、印ではなく、イベントの範囲を色つきの線で描くほうが自然だと考える（まだ決めていない） |

## 限界

- **評価の対象が、制御された計測**：同じ段差を何度も上り下りする計測で、通過の間隔が短い（中央値 4.2 秒）。実際の道では、段差はもっとまばらだと考えられるので、「まとめすぎ」の問題は、この評価より小さいはず（推測）。逆に、誤検知は、flat の走行（7.2 分）だけでは、実際の道の多様さ（坂、路面の継ぎ目、人の混雑）を表せない。
- **パラメーターを選ぶのも、同じ 16 走行**：判定の学習は走行ごとに分けたが、gap と min_n は、同じデータで選んだ（20 通りから選ぶだけなので、過学習は小さいと考える）。実際の道での確認は、12 月の評価で行う。
- **正解が粗い**：段差の正解は、衝撃の時刻 1 点。凸凹は、ラベルの区間（STOP を押すのが遅れた通過は除いてある）。
- **「誤検知」の定義**：段差のラベルの区間のうち、衝撃の ±1 秒に重ならない部分で出たイベントは、誤検知に数える。モデルは、その区間を「段差」として学習しているので、厳しめの数え方になっている。
- **関連研究は調べていない**：窓ごとの判定をまとめる方法について、論文は確認していない。論文や卒論で「このまとめ方を使った理由」を書くには、先行研究を調べる必要がある（`.claude/rules/feature-decision-rationale.md`）。
- **GPS が無い走行がある**：10/31 の走行には GPS が無く、速度は 11/1 の走行から求めた。

## 相談したいこと

1. **まとめ方の方針**：「続いた窓だけをまとめ、3 つ以上続いたものを採る」（gap 0・min_n 3）で、よいか。誤検知（flat の走行で 0.70 /分、約 85 m に 1 回）は、許せる範囲か。min_n 4 にすると、誤検知は 0.42 /分に減るが、凸凹の見逃しが少し出る（0.966）。
2. **段差の見え方**：重複した印（1 通過あたり 1.19 個）を、どう扱うか。地図の上で、近い印（例：2 m 以内）を、表示のときにさらに 1 つにまとめる案もある。
3. **凸凹の見せ方**：印ではなく、色つきの線（区間）で描いてよいか。
4. **評価の数え方**：12/7〜12/20 の実走行の評価（検出率・誤検知）は、「イベント単位」で数えることになる。窓単位の再現率（今の 0.95 前後）とは、数え方が違うことを、論文にどう書くか。
5. **位置の精度**：印の位置は、決定関数が最大の窓の中心で、衝撃から中央値 0.9 秒（約 0.9 m）、上位 10% で 4 秒ずれる。地図で見せるには十分か。衝撃の時刻（\|z\| の最大）で位置を補正する案もあるが、アプリで加速度を持ち続ける必要がある。
