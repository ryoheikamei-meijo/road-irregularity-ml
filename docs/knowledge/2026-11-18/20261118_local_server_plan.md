## 完了の判定（観測のしかた）

以下がすべて満たされたら完了とする（推測：私が置いた基準。合意を待つ）。

1. `npm run up` で PostgreSQL・S3 互換のストレージ（SeaweedFS）が立ち、`npm run dev` でサーバーが動く。
2. エミュレーターのアプリで 60 秒以上の判定を行うと、判定結果が数秒ごとに届き、DB の件数とクラスが、アプリの `judge.csv` と一致する。
3. 各判定に、緯度・経度・精度が入っている（エミュレーターの擬似位置）。
4. 走行後に自動で `input.csv`（ジャイロを含む）がストレージに届き、元のファイルとハッシュが一致する。
5. 通信を切って戻したときに、判定結果の欠けも二重もない。
6. キーが無いリクエストは拒否される。
7. 既存のアプリの単体テスト（`ParityTest`）が通ったままである。

## AWS Emulator について分かったこと（2026-11-18 に公式ページで確認）

出典：[ブログ](https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/)、[製品ページ](https://aws.amazon.com/products/developer-tools/emulator/)、[ユーザーガイド](https://docs.aws.amazon.com/emulator/latest/userguide/what-is-service.html)、[GitHub](https://github.com/aws/aws-emulator)。日本語版のブログは本文を取得できず、英語版と文書を読んだ。

**確認できたこと**
- AWS 公式。Rust 製。AWS アカウント不要、追加料金なし。ソースは CC0（`vendor/` のみ Apache-2.0）。
- Mac では Docker で動かす。**出来合いのイメージは公開されておらず、公式の Dockerfile から自分でビルドする**。
- 起動すると `https://127.0.0.1:9297` で待ち受け、SDK は `AWS_ENDPOINT_URL` で向ける。Node.js の SDK は `NODE_EXTRA_CA_CERTS` に `ca.pem` を渡す。
- 状態はメモリ上だけで、**停止すると全部消える**。IAM は AWS どおりには評価しない。長時間の利用・負荷試験は未検証。
- 未実装の操作は HTTP 501（`NotImplemented`）を返す。サービスごとの一致度（fidelity）は「k of n」で公開される。
- API Gateway と Lambda の連携のテストは、評価用スイートにある（`apigateway__lambda` など）。

**確認できなかったこと（今回の決定に直結する）**
- Lambda：関数を実際に動かすか、**Node.js を動かせるか**は記載なし（リリースノートの題名に Python のランタイムがあるのみ）。6 MB の上限を再現するかも記載なし。
- S3：**署名付き URL が使えるか**、100 MB 超のアップロードができるかは記載なし。
- RDS・Aurora：**本物の PostgreSQL が動いて SQL を実行できるか**は記載なし。
- 対応サービスの全体の一覧と、サービスごとの fidelity の数値は読めなかった。

## 段階 0（AWS Emulator の検証）の結果

2026-11-18 に実施。Apple Silicon の Mac で、公式文書の Dockerfile（arm 版の rpm）からイメージをビルドし（1.3 GB）、テレメトリをオフにして起動した。バージョンの表示は取っていない（`LTS/latest` のパッケージ。公開から 1 週間）。検証に使ったファイルは [`aws_emulator_spike/`](aws_emulator_spike/)。

| 検証 | 結果 | 内容 |
| --- | --- | --- |
| 疎通・S3 の基本 | ○ | SDK・CLI から `AWS_ENDPOINT_URL` で向ければ、STS・S3（バケット作成、PUT、GET）が動く |
| ② 署名付き URL | **△ 仕組みは動くが、上限で 100 MB は入らない** | Node.js の SDK で発行した署名付き URL で、PUT・GET と**分割アップロード**（10 MB × 4 = 40 MB）が動き、ハッシュも一致した。ただし **1 回の PUT は 16 MiB まで**（17 MB は 413）、**バケット全体で 64 MiB まで**（超えると `ValidationException`。失敗した分割アップロードの残りも数えられた）。100 MB は、単発でも分割でも入らない。上限を変えるオプションは見つからなかった |
| ① Node.js の Lambda | **△ 単純な関数は動くが、本物の Node.js ではない** | 作成・実行でき、返り値も正しい。ただし実行環境は**互換レイヤー**に見える：`process.version` は `v22.0.0` だが、`net`・`tls`・`dns`・`zlib`・`perf_hooks`・`worker_threads`・`util/types` が無く、`fetch` も未定義（`crypto`・`fs`・`http`・`https`・`stream` などはある）。作成直後は `Pending` で、実行は `Active` を待つ必要がある。Python のランタイムは作成までで、実行は確かめていない |
| ③ Lambda から PostgreSQL | **× つながらない** | Docker の本物の PostgreSQL（`postgres:17`）は立ったが、Lambda 側で `pg` を読み込む時点で `Cannot find module 'util/types'`（`net` も無いため、仮に読めても TCP の接続はできない） |

**読み取れること**
- エミュレーターで確かめられるのは、署名付き URL の**手順そのもの**（URL の発行 → 直接アップロード → 取得）と、**小さな関数**の実行まで。
- 生データの実サイズ（50〜160 MB）の送信、DB ドライバーを使う Lambda は、エミュレーターでは確かめられない。本番の AWS で確かめる項目になる。
- 検証した 1 つのバージョンの結果であり、今後のバージョンで変わる可能性がある（公式の fidelity の数値も未確認）。

**分かったこと・直したこと**
- **アプリの時刻は epoch ではない**：`timestamp` は端末の起動からの ms（`event.timestamp`）。研究の記録（epoch）とは基準が違うので、サーバーに壁時計の列 `window_wall_ms` を足した（migration 002。起動時に「壁時計 − `elapsedRealtimeNanos`」のずれを測り、窓の始まりに足す）。値は `started_at`（13:44:33 JST）と整合した。
- **SeaweedFS は起動直後の数秒、最初の PUT が失敗する**（書き込みの内部ロックの準備ができるまで）。サーバーの起動時とテストの準備で、実際に書けるまで待つようにした。
- **署名付き URL のホスト**：エミュレーターからは `10.0.2.2:8333`、PC からは `127.0.0.1:8333`。署名にホストが入るので、サーバーの `S3_PUBLIC_ENDPOINT` で切り替える。PC から送るスクリプトとエミュレーターを同時には使えない。
- PC の照合スクリプト `e20261116_check_device_session.py` の既定の版が古かったので、`v4_20261118` に直した。

**確かめていないこと**
- エミュレーターの仮想センサーは静止状態のため、判定が全部 flat。step・rough のクラスの対応は、PC からの送信（3 走行）でしか確かめていない。実機での走行は、このフェーズの外。
- 位置情報の権限の要求画面（`adb shell pm grant` で付けた）。従量課金の回線では生データを送らないこと。
- 通信が切れたときの端末での再送・WorkManager のやり直しは、単体テスト（偽のサーバー）まで。実際にサーバーを止める確認は ③。
- エミュレーターの GPS は 1 点を繰り返すだけで、実際の移動・精度の悪化は見ていない。

## 段階 ③ の結果（2026-11-18）

エミュレーターで、実際にサーバーを止めたり、アプリを強制終了したりして、再送を確かめた。照合は、端末のファイル（`detections.jsonl`・`input.csv`）と、DB・S3 の保存内容を、窓の集合と sha256 で比べた。

| シナリオ | 内容 | 結果 |
| --- | --- | --- |
| A | 走行（60 秒）の 15 秒目にサーバーを止め、45 秒目に戻す | ○ 116 窓。止まっている間は「通信できない」を繰り返して端末に残し、戻ったあとに送れた。欠け 0・余り 0、生データも一致 |
| C | 走行（40 秒）の途中でサーバーを止め、走行が終わったあとも止めておき、あとで戻す | ○ 76 窓。走行終了時は 7 / 76 窓。WorkManager が 30 秒・60 秒と間隔をあけてやり直し、サーバーが戻ったあとの 3 回目で完了。欠け 0・余り 0 |
| B | サーバーが止まったまま走行を始め、20 秒余りでアプリを強制終了し、サーバーを戻してから起動し直す | ○ 45 窓（送れた件数 0 から）。起動時に、送り終えていない走行を入れ直して送れた。欠け 0・余り 0 |
| （偶然） | 走り始めに姿勢が全部 0 のサンプルが届き、アプリが落ちた走行 | ○ 修正後の最初の起動で、残っていた分（生データ 16,384 バイト）が自動で届いた |

どのシナリオでも、DB の件数は「重複なしの件数」と同じで、二重の保存は無かった。

**ここで見つかったバグ（修正済み）**
- **走り始めに、姿勢（rotation vector）が全部 0 のサンプルが届くことがある**（エミュレーターの起動直後に確認）。長さ 0 の四元数で割って NaN になり、判定のスレッドが落ちてアプリが終了した。さらに、NaN が「直近 10 秒の平均」の合計に入ると、引き算しても消えず、その走行の傾きが以後ずっと NaN になる。
  - 直したこと：壊れたサンプル（非有限・長さ 0 の姿勢）は、状態に触れずに捨てる（`CoreFeatureExtractor.push`、姿勢を受け取る側）。判定結果に NaN があれば、送らずにログへ（`DetectionRecord.toJsonOrNull`）。1 件の保存の失敗で判定のスレッドが落ちないようにした。
  - テスト：壊れたサンプルを混ぜても結果が変わらないこと、NaN の判定結果・位置を外して送ること（新規 4 件）。
- 単体テストと実機の確認の両方で、この種の「走り始めの 1 サンプル」は、実機でも起こりうる（推測）。

**分かったこと（制限）**
- **強制終了したとき、`input.csv` の末尾が欠ける**：書き込みにバッファを使っているので、最後の 8 KB 程度（約 0.25 秒分）が残らない。判定結果（`detections.jsonl`）は 1 件ずつ書くので、欠けない。シナリオ B の生データは 335,872 バイトで、8,192 の倍数だった。`judge.csv` も、強制終了すると空になる（研究用の記録で、送らない）。
- **やり直しの間隔**：WorkManager の初回は 30 秒、その後は指数的に延びる。サーバーが戻ってから届くまで、最大で 1 分ほどかかった。

## 設計の下書き（推測。着手時に直してよい）

- **API**：`POST /sessions`、`POST /sessions/{id}/detections`（バッチ）、`POST /sessions/{id}/raw-upload-url`（署名付き URL を返す）、`POST /sessions/{id}/raw-complete`
- **表**：session（アプリが作る UUID、端末 ID、開始時刻、アプリ・モデルの版、車椅子・体重は空欄可）、detection（走行 ID と窓の始まりが主キー、時刻、緯度・経度・精度、クラス、決定関数の値、窓の長さ）、raw（走行 ID、保存先、大きさ、ハッシュ、送信日時）
- **ローカル**：`docker compose`（PostgreSQL、S3 互換のストレージ（SeaweedFS））とサーバー。Lambda 用の入口はデプロイのときに足す（コードは入口に依存しない作りにする）。
- **まとめて送る間隔**：5 秒を初期値にする。
